# §116 FIM: inline shell completion on a synthetic case set, three models, two modes

> Excerpt of §116 of a private lab notebook; paths, service names and hosts are generalised. The case set is
> generated in code (`tests/fim.py`): 29 self-authored shell lines, two cut points each. No shell history and
> no path from the lab's machine is in this repo.

**Why this is a re-run.** The lab first measured inline completion on 58 cases, 40 of them cut from the
owner's bash history. Those cases cannot be published, and they also flattened the ranking: every model
scored 0.20-0.27 on the history third, which is what pulled the whole table into a narrow band. This run
keeps the question and rebuilds the fixture so that anyone can repeat it.

**Method.** One throwaway server per model (build 12211, `-c 2048 --fit on --fit-target 64`, 4 threads), the
router seat unloaded first. Temperature 0, at most 16 tokens generated, stop on space or newline. The model
is shown the text typed so far and must return the rest of the word the cursor sits inside. Two modes:

- `fim`: posts `input_prefix` and `input_suffix` to llama.cpp's `/infill`, which is what a model trained for
  fill-in-the-middle expects.
- `plain`: posts only the prefix to `/v1/completions`, the control, and the only option for a model without
  FIM tokens.

Grading is code-side and strict: the **first token of the reply must equal the missing remainder exactly**,
so `oads/` for `oads` fails. Failures are classified as wrong, overlong (kept going past the answer), fenced
(backticks or think tags), empty, or echoed prefix.

**Result: 58 cases, one pass per arm.**

| model | fim | plain | fim − plain | fim latency mean / p95 |
|---|---|---|---|---|
| qwen2.5-coder-1.5b Q8_0 | **27/58 (0.466)** | 12/58 (0.207) | +0.259 | **114 ms / 142 ms** |
| granite4:3b-h | 24/58 (0.414) | 6/58 (0.103) | +0.311 | 272 ms / 529 ms |
| qwen2.5-coder-0.5b Q8_0 | 17/58 (0.293) | 10/58 (0.172) | +0.121 | **66 ms / 63 ms** |

**What the numbers say.**

- **Native FIM is the difference, not model size.** Every model gains from `/infill`: +0.26, +0.31, +0.12.
  The 3B gains the most and is still the slowest by a wide margin; its p95 of 529 ms is outside a
  sub-250 ms ghost-text budget, which is the requirement this job actually has.
- **The 1.5B is the seat.** Best accuracy of the three at 114 ms mean and 142 ms p95 in 1.65 GB of VRAM.
- **The 0.5B buys latency, not accuracy:** 66 ms mean (its p95 reads below the mean because the mean is
  dragged by the first, cold requests), but 17 points behind the 1.5B.
- **Read the order carefully.** On the earlier, partly history-derived set the 1.5B sat mid-pack (0.345)
  behind a 3B (0.405). Here it leads. A hard subset that no model passes compresses the top of a table, and
  the history lines were exactly that. On all-synthetic path and flag cases the ordering is cleaner and this
  model's native FIM does well. Both statements are true of different case sets; the published table is this
  one, and its numbers are not comparable with the earlier run's.
- **Failure shape.** Misses are almost all `wrong` (a different word or path); very few are empty or overlong,
  and no model produced backticks or think tags here. The 3B returned 6 empty replies and 2 overlong ones.

**Not re-run.** qwen2.5-coder-3b, starcoder2-3b, codegemma-2b, deepseek-coder-1.3b and the two granite
micro variants were measured in the earlier run and deleted afterwards; re-downloading them is about 13 GB
and this table covers the range the seat decision needs. Their earlier scores stay on the lab's record and are
not comparable with these rows.

**Caveats.** One pass per arm, 58 cases, one card, one build; 2 cases is noise. Plain mode cannot see the
suffix, so it is a floor rather than a fair fight. Containers start immediately before the test, so the first
cases carry cold-load latency and the p95 of the slow models is slightly pessimistic. A first pass of this
run scored 0/58 because the test posted to `/v1/infill` instead of `/infill`; those records were discarded
after the fix, and a transport error is now recorded as a transport error rather than as an empty reply.
